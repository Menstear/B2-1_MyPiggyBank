# 100k 거래의 성능과 병목 분석

## 측정 방법

프로젝트 루트에서 다음 명령을 실행합니다. Python 표준 라이브러리만 사용하며 실제 `./data`에 접근하지 않습니다.

```bash
python -m benchmarks.benchmark --rows 100000 --repeat 3 --memory --output /tmp/budget-100k.json

# 필요한 유스케이스만 측정
python -m benchmarks.benchmark --rows 100000 --repeat 3 --cases search_all import

# 정렬의 청크 / 병합 입력 수 / 파일 버퍼 비교
python -m benchmarks.benchmark --rows 100000 --repeat 3 --cases search_all --memory \
    --chunk-size 5000 --fan-in 32 --io-buffer-size 8192
```

입력은 2024년 366일에 걸쳐 날짜를 섞은 100,000건입니다. 기본 카테고리 5개, 한글·쉼표가 있는 메모와 태그 2개를 사용합니다. 한 번 만든 입력으로 각 유스케이스를 별도 프로세스에서 3회 실행합니다. `list`와 제한 검색은 20건, 전체 검색과 CSV 입출력은 100,000건, 요약은 3월, 추가/수정/삭제는 한 건을 처리합니다. 가져오기는 **빈 거래 파일**에 수행하며, 다른 작업은 100,000건이 저장된 파일을 대상으로 합니다.

시간은 `perf_counter`로 측정하며 데이터 생성·초기화·파일 복사·프로세스 시작·터미널 출력을 제외합니다. 전체 검색은 끝까지 소비하면서 날짜/숫자 ID 순서와 결과 건수를 검증합니다. 파일 생성/복사가 측정 직전에 수행되므로 파일 캐시의 영향을 받으며, 차가운 디스크 캐시를 통제한 측정은 아닙니다. 실행 중 다른 무거운 작업을 피하고 같은 환경에서 비교하세요.

JSON 결과에는 환경, 설정, 각 실행의 시간, 중앙값/최솟값/최댓값, 결과 건수가 들어 있습니다. `max_peak_rss_mib`는 준비 과정을 포함한 프로세스 전체의 최대 RSS이고, `python_peak_mib`는 `--memory`로 별도 실행한 작업 중 Python 할당 추적의 피크입니다. 두 값은 의미가 다르며, 메모리 추적 실행은 일반 시간 표본에 포함하지 않습니다. Windows에서 RSS가 제공되지 않으면 `null`로 기록하고 시간/메모리 추적은 계속 사용할 수 있습니다.

## 실측 결과

2026-10-11, Python 3.13.12, macOS/Darwin 25.6.0, arm64, 논리 CPU 8개에서 측정했습니다. 수치는 이 입력과 환경의 관찰 결과이며 다른 디스크·메모 길이·검색 조건에서 같은 시간을 보장하지 않습니다.

개선 전 전체 결과는 [baseline-100k.json](benchmarks/baseline-100k.json), 개선 후 결과는 [improved-100k.json](benchmarks/improved-100k.json)에 보관했습니다. 개선 전은 이번 변경 전 코드(청크 1,000건, 런타임 기본 버퍼)이고, 개선 후는 카테고리 1회 조회·고정 스키마 직렬화·ISO 날짜 정규화·청크 5,000건·8KiB 정렬 버퍼를 사용합니다.

| 유스케이스 | 개선 전 중앙값 | 개선 후 중앙값 | 개선 후 작업 중 Python 피크 |
| --- | ---: | ---: | ---: |
| 목록 20건 | 0.250초 | 0.251초 | 0.070MiB |
| 제한 검색 20건 | 0.262초 | 0.264초 | 0.071MiB |
| 전체 검색 100k | 1.595초 | 0.881초 | 3.590MiB |
| 3월 요약 | 0.236초 | 0.259초 | 0.265MiB |
| CSV 내보내기 100k | 0.347초 | 1.119초* | 0.196MiB |
| CSV 가져오기 100k | 9.263초 | 1.103초 | 0.304MiB |
| 한 건 추가 | 0.242초 | 0.248초 | 0.267MiB |
| 한 건 수정 | 0.636초 | 0.507초 | 0.070MiB |

가져오기는 약 **88%**, 전체 검색은 **45%**, 수정/삭제는 **20~22%** 시간이 줄었습니다. 제한 조회/추가 등의 전체 스캔 비용은 줄이지 않았습니다. 결과는 세 변경의 결합 효과이며 각 변경의 단독 기여도로 분해한 측정은 아닙니다.

\* 내보내기의 최종 전체 실행 표본은 1.895/1.119/0.420초로 변동이 컸습니다. 내보내기 경로의 시간 증가를 확인하기 위해 같은 최종 코드로 [별도 5회 재측정](benchmarks/recheck-export-100k.json)했고, 0.351~0.362초, 중앙값 **0.354초**였습니다. 불리한 전체 실행 표본도 원본 결과에 남겼습니다. 내보내기의 속도 개선을 주장하지 않으며, 변동의 원인을 특정 함수나 디스크 동기화로 단정하지 않습니다.

카테고리 조회/직렬화/정렬 개선 직후의 [중간 측정](benchmarks/intermediate-100k.json)에서 가져오기는 9.263초 → 6.708초였습니다. 남은 비용을 `cProfile`로 확인한 [프로파일 요약](benchmarks/import-profile.txt)에서 날짜 검증의 누적 시간은 6.583초이고 그중 `strftime` 자체가 5.666초였습니다(프로파일 계측 실행의 시간으로 일반 벤치마크와 직접 비교하지 않음).

10월 11일 개선에서는 날짜를 파싱/검증하는 `strptime`은 유지하고, 정규화는 `parsed.date().isoformat()`으로 변경했습니다. 월은 검증한 연도·월을 자릿수 지정으로 조합합니다. 10월 14일에는 아래와 같이 정규 날짜의 파싱 경로도 단축했습니다. 날짜/월 캐시를 추가하지 않아 입력 종류에 비례하는 메모리 증가도 없습니다. 기존 비정규 날짜 정규화와 윤년 검증을 유지하고 0001~9999 연도의 네 자리 표현도 테스트합니다.

같은 Python 3.13.12/macOS 환경과 100k 입력에서 각 작업을 3회 측정했습니다. 이번 수정 직전 리뷰의 [원본 표본](benchmarks/review-before-20261014-100k.json)과 수정 후 [원본 표본](benchmarks/review-fixes-20261014-100k.json)을 함께 보관합니다. 이 재측정에서는 `--memory`를 사용하지 않았으므로 작업 중 Python 할당 피크는 측정하지 않았습니다.

CSV 가져오기 시간은 이 측정에서 약 **34% 감소**했습니다. 정규 날짜에 `date.fromisoformat()`을 사용하는 빠른 경로를 적용하면서도 CSV 열 개수/중복 헤더 검사를 보강한 결과입니다. 이는 전체 변경의 결합 측정이며 파서만의 단독 기여도를 측정한 값은 아닙니다. 수정 직전 가져오기 표본은 0.879~2.011초로 변동이 있었고, 캐시·실행 시점 등의 영향을 통제한 인과 실험은 아닙니다. 대량 검색 알고리즘이나 정상 ID 수정·삭제의 전체 재작성은 유지했으므로 다른 행의 시간 차이를 새로운 알고리즘의 효과로 단정하지 않습니다.

이번 개선 중 조건부 비용 제거는 시간 임계값 대신 회귀 테스트로 확인했습니다.

- 검색에 일치한 결과가 0~5,000건이면 임시 디렉터리 생성과 JSON 재직렬화를 생략합니다. 한계를 한 건 넘으면 기존 외부 정렬로 전환하며 메모리·파일 핸들 상한을 유지합니다.
- 빈 CSV, 잘못된 헤더, 모든 행을 건너뛴 CSV에서는 다음 ID를 찾으려고 거래 파일을 읽지 않습니다. 정상 행이 있으면 다음 ID를 최초 한 번 구하고 정상 거래에만 연속 번호를 부여합니다.
- 없는 ID의 수정·삭제는 원본을 교체하거나 `fsync`하지 않습니다. 추가 ID 사전 조회를 넣지 않았으므로 성공 경로도 한 번의 전체 읽기를 유지합니다. 임시 파일 작성과 닫기 시 버퍼 쓰기는 남습니다.
- 검색 날짜/타입은 `SearchQuery` 생성 시 한 번만 검증·정규화하여 CLI와 직접 서비스 호출이 같은 규칙을 사용합니다.

이 성능 측정 단계에서 전체 135개 테스트가 통과했으며, 보너스 기능을 추가하지 않고 기존 명령과 저장 방식 안에서 수정했습니다.

### 청크와 버퍼 비교

아래 비교는 카테고리/직렬화 개선 후, ISO 날짜 정규화 변경 전에 같은 코드에서 정렬 설정만 바꾸었습니다. 전체 검색은 저장된 날짜를 비교하므로 입력 날짜 검증/정규화를 실행하지 않습니다. 병합 fan-in은 모두 32입니다. 원본 표본은 [1k/64KiB](benchmarks/tuning-1000-65536.json), [5k/64KiB](benchmarks/tuning-5000-65536.json), [10k/64KiB](benchmarks/tuning-10000-65536.json), [5k/8KiB](benchmarks/tuning-5000-8192.json)에 있습니다.

| 청크 크기 | 버퍼 | 전체 검색 중앙값 | 작업 중 Python 피크 | 전체 프로세스 최대 RSS |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 64KiB | 1.663초 | 3.34MiB | 29.38MiB |
| 5,000 | 64KiB | 0.828초 | 3.59MiB | 31.75MiB |
| 10,000 | 64KiB | 0.839초 | 7.14MiB | 35.33MiB |
| 5,000 | 8KiB | 0.831초 | 3.59MiB | 31.81MiB |

청크 1,000건은 100개의 초기 정렬 파일을 만들고 32개가 모일 때마다 중간 병합 파일을 작성합니다. 청크 5,000건은 초기 파일 20개를 최종 병합에서 바로 읽으므로 중간 파일을 다시 쓰고 파싱하는 비용을 줄입니다. 10,000건은 이번 입력에서 추가 속도 이득 없이 메모리 피크가 약 2배로 늘어 **5,000건을 기본값**으로 선택했습니다. 8KiB와 64KiB의 시간 차이는 1% 미만이므로 큰 버퍼의 효과로 해석하지 않고 작은 버퍼를 유지했습니다.

거래 수가 더 커져 초기 파일이 32개를 넘으면 중간 병합은 다시 필요합니다. 100k에서 관찰한 개선 비율을 모든 데이터 크기에 그대로 적용할 수 없습니다. 긴 메모가 많은 데이터에서는 같은 청크 건수도 더 많은 메모리를 사용하므로 1,000건 등 작은 청크와 함께 재측정해야 합니다.

## 병목별 분석과 적용한 개선

| 경로 | 100k에서의 비용 / 원인 | 적용한 개선 | 남은 비용 |
| --- | --- | --- | --- |
| CSV 가져오기 | 기존에는 각 행마다 카테고리 파일을 재조회하고, 유효 행이 없어도 거래 파일에서 다음 ID를 탐색 | 카테고리를 한 번 읽어 집합으로 유지. ID 탐색은 첫 정상 행까지 지연하며 이후 메모리에서 증가 | 정상 행이 있으면 기존 거래 전체 ID 스캔과 재작성. 각 CSV 행 검증과 JSON 인코딩 |
| 날짜 정규화 | 중간 프로파일에서 `strftime`의 반복 호출이 가져오기 비용 대부분을 차지. 이후에도 범용 `strptime` 파싱 비용이 남음 | 정규 YYYY-MM-DD는 `date.fromisoformat`, 비정규 입력만 기존 `strptime`; `date.isoformat()`으로 정규화 | 달력 검증은 매 행 유지. ISO 주차·구분자 생략 등 다른 문법은 받아들이지 않음 |
| 전체 검색 | 정렬 묶음 및 중간 병합에서 JSON 파싱/직렬화, 파일 열기/쓰기. 소량 검색에도 임시 파일을 사용하던 비용 | 일치 결과 5,000건까지 메모리 정렬, 초과할 때만 외부 정렬. 청크 5,000·fan-in 32·명시적 버퍼 유지 | 전체 입력 스캔과 대량 결과의 최종 병합; 첫 결과 전 입력을 끝까지 읽어야 함 |
| JSON 저장·정렬 | `dataclasses.asdict`의 범용 필드/구조 탐색을 거래마다 수행 | 고정 필드 dict 생성. 변경 가능한 `tags`만 복사하여 기존 결과와 독립성 유지 | JSON 자체의 인코딩/디코딩 비용. 이 변경 단독의 속도 기여는 따로 측정하지 않음 |
| 제한 조회 / 월 요약 | 결과가 20건 또는 한 달이어도 거래 파일 전체를 읽고 JSON 객체를 생성 | 제한 조회는 최신 K건 힙, 요약은 카테고리별 카운터만 유지하는 기존 구조 유지 | 시간은 N에 따라 증가. 제너레이터는 메모리를 줄이지만 스캔을 없애지는 않음 |
| 단건 추가 | 다음 TX 번호를 구하기 위해 전체 파일을 스캔한 뒤 한 건 append·`fsync` | 가져오기에서는 번호를 한 번 구한 후 메모리에서 증가. 단건 추가의 기존 복구 전략 유지 | 단건 추가는 여전히 O(N); 한 건씩 대량 추가하면 누적 비용이 커짐 |
| 수정·삭제·카테고리 재분류 | 변경이 한 건이어도 전체 파일을 파싱해 임시 파일에 다시 작성 | 직렬화 비용 감소, 스트리밍 재작성 유지. update/delete 대상이 없으면 `fsync`와 원본 교체를 생략 | 대상이 없어도 한 번의 전체 읽기와 임시 파일 작성은 필요. 카테고리 재분류는 별도로 벤치마크하지 않음 |
| 내보내기 / CLI 출력 | CSV 레코드를 쓰고 동기화. 전체 검색 CLI는 출력까지 100k번 수행 | 내보내기는 정렬이 필요 없는 삽입 순서 스트리밍 유지 | 터미널 렌더링/파이프 속도는 별도 비용이며 이 벤치마크에서 제외 |

`I`는 CSV 입력 행 수, `C`는 등록 카테고리 수입니다. 집합 검사 비용은 평균적인 해시 조회를 전제로 합니다. 카테고리 목록은 가져오기 한 번 동안의 스냅샷이며 다음 실행에는 다시 읽습니다. 오류 리포트는 첫 5건만 보관하고 모든 건너뛴 행을 집계하므로 오류 수에 비례해 목록이 커지지 않습니다.

## 시간·메모리·디스크 비용

`N`: 저장 거래 수, `K`: 제한 건수, `M`: 정렬 청크 크기(5,000), `F`: 병합 입력 수(32), `R ≈ ceil(N/M)`: 초기 정렬 파일 수. 아래는 고정 크기의 거래를 가정한 분석이며 실제 메모리에는 가장 긴 레코드와 텍스트 버퍼도 영향을 줍니다.

| 작업 | 시간 비용 | 작업 메모리 | 디스크 / 첫 결과 시점 |
| --- | --- | --- | --- |
| `list` / 제한 `search` | 전체 스캔 + O(N log K) 상한 | O(K) 거래 | 임시 정렬 파일 없음. 전체 스캔 후 출력 |
| 전체 `search` | 청크 정렬·병합 비교는 O(N log N) 상한; 추가 I/O는 병합 단계 수에 따라 증가 | 소량은 최대 M건, 대량은 O(M+F) 거래 + O(F log_F R) 임시 경로, F개 입력 버퍼 | 일치 결과 ≤ M이면 정렬용 임시 파일 없음. 초과하면 임시 디스크 O(N). 전체 스캔 후 출력 |
| `summary` | O(N), 별도 예산 조회 | O(C) 카운터 | 전체 스캔 후 집계 반환 |
| `export` | O(N), 출력 건수에 비례한 CSV 쓰기 | 거래 한 건 / 행 버퍼 | 출력 CSV용 임시 파일, 끝까지 성공한 뒤 교체 |
| `import` | 정상 행이 있을 때만 기존 파일 최대 2회 스캔 + 입력 검증/쓰기 O(I+C) | 카테고리 O(C) + 행 하나 + 최대 5건 오류 샘플 | 정상 행이 없으면 거래 파일 I/O 없음. 있으면 기존 N건 + 정상 입력을 임시 파일에 쓰고 한 번 교체 |
| 단건 `add` | ID 탐색 O(N) + append | 거래 한 건 | append만큼 쓰며 실패 시 원래 길이로 복구 |
| `update` / `delete` | O(N) 전체 재작성 | 거래 한 건 | 원본 크기에 가까운 임시 파일 공간 필요. 없는 ID는 임시 파일만 지우고 원본 보존 |

원본과 임시 파일은 저장 중 함께 존재합니다. 전체 검색은 저장소 폴더가 아닌 운영체제 임시 폴더에 정렬 파일을 만듭니다. 여유 공간과 권한은 두 위치에서 확인해야 합니다. I/O 실패를 주입하는 테스트는 원본 보존과 임시 파일 정리를 검증하며 실제 100k 디스크 부족이나 강제 종료를 재현한 테스트는 아닙니다.

## 더 큰 데이터에서 검토할 개선안

다음은 현재 구현에 포함되지 않은 후속 설계입니다. 프로파일과 다른 입력/디스크에서의 재측정으로 비용을 확인한 뒤 선택해야 합니다.

1. **월별/날짜/ID 인덱스 또는 SQLite**: 제한 조회·요약·단건 추가의 전체 스캔을 줄입니다. JSONL에 보조 인덱스나 마지막 ID 메타 파일을 붙이면 원본 교체 실패, 수동 편집, ID 복구 시 두 파일의 일관성 처리가 필요합니다. 동시 쓰기와 더 빠른 수정도 필요하다면 표준 라이브러리 `sqlite3`의 트랜잭션/인덱스를 비교하는 편이 명확합니다.
2. **청크·fan-in·버퍼 튜닝**: 청크를 키우면 중간 병합 I/O는 줄지만 거래 객체 메모리가 늘어납니다. fan-in을 키우면 병합 단계는 줄지만 파일 핸들과 버퍼가 늘어납니다. 100k, 1M, 긴 메모 입력에서 시간·RSS·할당 피크·임시 디스크를 같이 비교해야 합니다. 현재 기본값은 이 100k 실측을 기준으로 합니다.
3. **병렬 정렬**: CPU가 병목일 때 독립 청크를 프로세스에서 정렬하는 실험이 가능합니다. 작업자 수×청크 메모리, 프로세스 시작/데이터 전달/직렬화 비용, 디스크 경합이 추가됩니다. 결과 순서, 작업자 예외 시 모든 임시 파일 정리, 파일 핸들 상한을 유지해야 합니다. 단순히 스레드만 추가하면 빨라진다고 가정하지 않습니다.
4. **비동기 I/O / 읽기 선행**: 느린 저장장치에서 읽기 대기와 계산이 겹칠 때, 제한된 큐로 다음 청크를 미리 읽는 실험을 고려할 수 있습니다. 큐 상한과 취소/예외 처리가 필요하고, 이미 버퍼링된 로컬 파일이나 JSON 파싱이 병목인 경우 이득이 작을 수 있습니다. 동기 코드에 `async`를 붙이는 것만으로 파일 작업이 빨라지지 않습니다.
5. **CSV 검증 프로파일**: 정규 날짜 전용 파서를 적용한 뒤에도 검증과 JSON 변환은 행마다 수행합니다. 추가 최적화는 다시 프로파일한 결과를 기준으로 선택해야 합니다. 날짜 캐시를 도입한다면 상한을 두고, 비정규 입력 정규화·윤년·잘못된 날짜 거부 규칙을 유지해야 합니다. 입력마다 달라지는 문자열을 무제한으로 캐시하지 않습니다.
6. **대량 출력·저장 정책**: 터미널 출력량이 크면 `--limit`/검색 필터를 사용하거나 파일로 리다이렉트해 출력 비용을 따로 측정합니다. 반복 추가는 CSV 일괄 가져오기로 한 번에 반영할 수 있습니다. 성능 개선을 위해 저장 성공의 의미를 약화시키는 `fsync` 제거는 적용하지 않았습니다.

정렬 테스트는 작은 청크/fan-in으로 여러 병합 단계를 강제로 만들고 숫자 ID·날짜 정렬, 생존 거래 객체/파일 핸들 상한, 완료/중단/오류 시 정리를 검증합니다. 가져오기 테스트는 카테고리 1회 조회, 실행 사이 갱신, 리포트 샘플 상한/물리 행 번호, 늦은 파싱·저장 실패 시 원본 보존을 확인합니다. 직렬화 테스트는 전체 필드의 왕복과 태그 복사, 벤치마크 테스트는 모든 유스케이스의 실행과 데이터 격리를 확인합니다.

10월 14일 회귀 검증에서는 소량/빈 검색의 임시 파일 미생성, 정상 행 없는 CSV의 거래 스캔 생략, 중복 헤더·초과 값·누락 값 처리, 없는 ID 수정·삭제의 원본 바이트/inode 보존과 교체 생략, 줄바꿈 없는 JSONL 추가 및 실패 복구도 확인합니다. CLI는 버퍼 유무에 따른 파이프 중단, 음수 TOP, export 조건 충돌과 평년/윤년 월말, 서비스는 검색 조건 1회 정규화를 검증합니다.

이후 검토에서 발견한 출력 파일 쓰기 오류와 큰 금액의 사용률 계산도 별도 회귀 테스트로 검증합니다. stdout뿐 아니라 stderr의 로그·사용법 출력, 양쪽 버퍼 비우기, 한글을 표현할 수 없는 출력 인코딩까지 검사합니다. 출력 오류는 실제 파일 쓰기 한도 또는 실패 주입으로 재현합니다. 큰 금액은 실수 변환 없이 사용률을 계산하고, 합계가 Python의 정수 문자열 변환 제한을 넘어도 작은 단위로 나누어 변환하여 잔액·초과 경고·TOP까지 표시하는지 확인합니다. 위 성능 수치는 이 출력 오류 수정 전 측정값이며, 이 수정들의 속도 개선을 주장하는 자료는 아닙니다.

성능 테스트에 고정 시간 임계값을 두지 않습니다. 느린 CI나 다른 디스크에서 정상 구현이 실패하지 않도록 기능/자원 상한은 테스트로, 시간 변화는 반복 벤치마크의 표본으로 평가합니다.
